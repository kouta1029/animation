# 開発・制作データルール v0.1

この文書は`docs/production_rules.md`を**技術面で補完**する。総監督の承認ゲートと`docs/decisions.md`に優先しない。

## 1. 開発環境とツールの位置づけ

- 現時点の技術候補：**Godot**（2Dカットアウト）、必要に応じ**Blender Grease Pencil**、**Python／FFmpeg**（音声・字幕・合成・検査）。
- 上記は**検討中**。特定バージョンやアーキテクチャは検証・承認するまで必須条件にしない。
- Windows 11などの通常環境でも再現できる手順を優先。OS依存の絶対パスをソースへ直書きしない。
- 依存関係、実行コマンド、サンプル設定、必要リソース（RAM/VRAM等）をREADMEに残す。
- クラウドAPIを使う場合、シークレットは環境変数／安全な秘密管理に置く。ログにキーや個人情報を出さない。

## 2. リポジトリ構造

| パス | 正式用途 |
|---|---|
| `docs/` | 決定ログ、バイブル、仕様、レビュー記録 |
| `episodes/ep###/` | 各話のブリーフ・脚本・ショット・QA |
| `assets/characters/` | キャラの原画・分割PNG・リグ向け差分 |
| `assets/backgrounds/` | 固定背景・時間帯差分 |
| `assets/props/` | 小物・演出素材 |
| `audio/` | 話者設定、録音・生成音声、SE/BGMメタデータ |
| `animation/` | リグ、タイムライン、シーン、制作コード |
| `renders/` | レンダリング結果の索引・QA（大容量本体は別保管可） |

各話IDは`EP001`、カットIDは`EP001_SH010`、発話IDは`EP001_L001`のように一貫して管理する。決めたIDは参照側に影響するため、改名時は関連ファイルを同時に変更する。

## 3. 標準データ契約（案）

各話で原則用意する：

- `brief.md`：視聴者、狙い、尺、登場人物、演出・制作上の制約、G0承認
- `script.md`：発話ID、話者、全文、感情・話速、前後の間、場面の指示
- `shots.csv`：`shot_id,start_ms,duration_ms,speaker_id,line_id,asset_ids,camera,action,emotion`
- `audio_manifest.csv`：`line_id,speaker_id,model_or_source,voice_id,file_path,duration_ms,usage_rights`
- `asset_manifest.csv`：`asset_id,file_path,version,source,rights,owner`
- `qa.md`：確認環境、実施手順、結果、問題点、G4／G5状態

**重要**：ここに列挙した列は初期の**提案スキーマ**。パイロットで映像・脚本担当が照合し、総監督の承認後に固定する。各IDと時刻はできる限り機械的に検証する。

## 4. 作画・カットアウト素材

- マスターは再編集可能なレイヤー構造を保持。出力パーツは原則透過PNGで、フチ・余白・影を整える。
- 体・頭・左右の腕・手・脚、目・眉・口は個別に扱えるようにする。
- 各パーツに**ピボット（回転中心）・重なり順・基準スケール**を記録する。
- 基本は正面と左右3/4。反転時の左右非対称な服・小物・文字の破綻に注意する。
- 口形は最低限「閉・A/I/U/O」を候補とし、演出上の表情を別に用意する。
- 命名例：`nao_eye_open_normal_L.png`、`hibiki_mouth_o_big.png`。人名は**仮**なので正式名承認前にコードへ固定しすぎない。
- 画風・パーツ数の基準は`docs/character_design_parts_v0.1.md`を参照。

## 5. 音声・字幕・タイミング

- キャラの**同じ声が複数話で再現できること**を重視する。Voice ID、モデル版、設定値、生成日、利用条件を記録。
- ElevenLabsは**候補**。VOICEVOX／AivisSpeechなどと同一日本語台本で比較し、予算・発音・感情・権利条件で採否を判断。
- 発話を`line_id`で管理し、音声ファイル、字幕、口パク、演出の参照先を一致させる。
- 先に音声尺・無音を測定し、カットの実尺に反映する。根拠のない固定秒数でセリフを切断しない。
- 音量だけの口開閉は簡易試作と明記。改善時は母音・音素推定やセリフ時刻を使用する。
- BGM・SEは声の明瞭度を損ねない音量に調整し、過大音量・クリッピング・無音欠落をチェックする。

## 6. レンダリング・受入基準

| 出力 | 目標 | 注意 |
|---|---|---|
| Shorts | 1080×1920、9:16、30～60秒を初期目安 | 顔・字幕をYouTubeのUIが覆わない構図 |
| 長尺 | 1920×1080、16:9、6～10分から検証 | 同一カメラ・静止画だけで引き延ばさない |
| FPS | 作品単位で24/30fpsなどに固定 | フレームレート変換によるカクつきを検証 |
| MP4 | H.264映像＋AAC音声を基本候補 | 動画を実再生して色、音、字幕、同期を検証 |

数値は基本目標であり、企画ごとの正式仕様はG0/G2で確定する。

## 7. コーディング・自動化ルール

- 既存の実装スタイルに合わせ、変更範囲を必要最小限にする。無関係な大規模修正は別PR。
- 主要な関数には入力、出力、時刻単位（ms/s/frame）、失敗条件を明記。
- データを読み込む際、欠損した素材／未定義の話者／重複ID／時間重複を検出し、無言で代替しない。
- 変換処理は再実行できるようにする。入力・設定・出力先・コマンドを記録。
- 生成済み素材を上書きする場合は、どの版を更新するか事前に指定し、復旧可能性を確保。
- OS依存・外部サービスの差を隠さず、実行前提と未検証事項をREADMEに残す。

## 8. 最低限のテストと報告

- **文書・契約**：参照パスの存在、ID重複、未決定を確定扱いしていないか。
- **アセット**：画像の透過・寸法・左右、ファイル破損、ピボット・重なり。
- **動画**：全編再生、尺、映像音声コーデック、字幕見切れ、音ズレ、無音・音割れ。
- **素材権利**：音声サービスの商用条件、SE/BGM/フォント/画像の出典。
- **自動化**：失敗時のエラーを確認し、破損や途中中断時に再試行できるか。

PRには**実施コマンドと結果**、未実施なら理由を記録。環境がないのに「テスト済み」と書かない。
